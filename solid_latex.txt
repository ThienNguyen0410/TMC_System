\subsection{Attendance Module}

The Attendance module (\texttt{src/backend/modules/attendance}) records employee
check-in and check-out events using short-lived QR codes. It exposes endpoints to
create a QR code and scan one to record attendance. The backend validates the QR
token, optionally checks the scan location against the QR code location, verifies
that the linked employee is active, enforces a cooldown, and alternates between
\texttt{CHECK\_IN} and \texttt{CHECK\_OUT}. A successful database write also creates
an \texttt{attendance.recorded} event in the outbox.

\begin{table}[H]
\centering
\caption{Attendance module endpoints}
\label{tab:attendance-endpoints}
\begin{tabular}{|l|l|p{7cm}|}
\hline
\textbf{Endpoint} & \textbf{Access} & \textbf{Description} \\
\hline
\texttt{POST /api/attendance/qr-codes} & Authenticated user &
Creates a QR code for the authenticated user; optional location data can be included. \\
\hline
\texttt{POST /api/attendance/scan} & QR token &
Validates a QR token and records the next attendance event; an optional kiosk location is accepted. \\
\hline
\end{tabular}
\end{table}

The QR-code endpoint requires authentication through \texttt{requireAuth}. The scan
endpoint does not require a separate login session; possession of a valid,
unexpired, unused QR token is required. QR tokens expire after five seconds and
are stored as SHA-256 hashes rather than as plaintext tokens. When both the QR
code and the scan include a location, the module requires them to be within one
metre.

\subsubsection{Architecture}

The module follows a layered structure:

\begin{itemize}
  \item \texttt{routes/}: creates the Express router and applies authentication to QR-code creation.
  \item \texttt{controller/}: validates request bodies and maps service results to HTTP responses.
  \item \texttt{service/}: implements QR-code issuance and attendance-scan orchestration.
  \item \texttt{repository/}: defines small persistence contracts and provides the PostgreSQL adapter.
  \item \texttt{domain/}: contains attendance and QR-code types, pure rules, and domain errors.
  \item \texttt{testing/}: provides an in-memory implementation of both repository contracts.
  \item \texttt{infrastructure/external/hr-payroll/}: provides HTTP and logging adapters for the HR/payroll port.
\end{itemize}

relationships. Boxes marked \texttt{<<module>>} represent exported functions or
domain types rather than instantiable classes. The HR/payroll adapters are shown
because they implement a port declared by Attendance; their current integration
status is described under Limitations.

At application startup, \texttt{app.ts} acts as the composition root. It creates
one \texttt{PostgresAttendanceRepository}, passes it to \texttt{QrCodeService} and
\texttt{AttendanceService}, then injects both services into
\texttt{AttendanceController}. The router is mounted at
\texttt{/api/attendance}.

A scan request follows this sequence:

\begin{enumerate}
  \item The router forwards the request to \texttt{AttendanceController.scan}.
        The controller validates the token and optional location with Zod.
  \item \texttt{AttendanceService.scan} asks the injected \texttt{QrCodeValidator}
        to validate the token. In production this validator is
        \texttt{QrCodeService}, which hashes the token and rejects unknown,
        revoked, or expired QR codes.
  \item The service checks the QR and kiosk locations when both are available,
        loads the employee, rejects inactive accounts, and enforces the
        configured 30-second cooldown.
  \item The service chooses the next event using \texttt{nextAttendanceEvent}
        and calls \texttt{AttendanceRepository.createRecord}.
  \item The PostgreSQL adapter consumes the QR code, inserts the attendance
        record, and inserts an outbox event in one database transaction. The
        controller returns the confirmation with HTTP 201.
\end{enumerate}

\subsubsection{Single Responsibility Principle}

Each component has a focused responsibility and a corresponding reason to change:

\begin{table}[H]
\centering
\caption{Responsibilities of Attendance components}
\label{tab:attendance-srp}
\begin{tabular}{|p{6cm}|p{8cm}|}
\hline
\textbf{Component} & \textbf{Responsibility} \\
\hline
\texttt{createAttendanceRouter} & Declares endpoint paths and applies route-level authentication. \\
\hline
\texttt{AttendanceController} & Handles HTTP input and output, including request validation and response serialization. \\
\hline
\texttt{AttendanceService} & Orchestrates QR validation, location and employee checks, cooldown enforcement, and attendance creation. \\
\hline
\texttt{QrCodeService} & Creates QR tokens, stores their hashes, and validates their lifecycle. \\
\hline
\texttt{PostgresAttendanceRepository} & Encapsulates SQL queries and transaction handling for attendance and QR-code persistence. \\
\hline
\texttt{InMemoryAttendanceRepository} & Implements repository contracts using in-memory collections for tests. \\
\hline
\texttt{nextAttendanceEvent} & Determines the next check-in/check-out event from the previous event type. \\
\hline
\texttt{qr-code.ts} domain functions & Own QR-token hashing, expiry, token generation, distance calculation, and location-tolerance rules. \\
\hline
\texttt{attendance.schema.ts} & Validates the shape and bounds of QR-code and scan request data. \\
\hline
\texttt{attendance-errors.ts} & Defines domain-specific errors and their HTTP status/code information. \\
\hline
\end{tabular}
\end{table}

For example, the check-in/check-out rule is isolated from persistence and HTTP:

\begin{verbatim}
export function nextAttendanceEvent(
  previous: AttendanceEventType | null,
): AttendanceEventType {
  return previous === 'CHECK_IN' ? 'CHECK_OUT' : 'CHECK_IN'
}
\end{verbatim}

Similarly, the QR-code module contains pure functions for expiry and location
distance. Changing a request field affects the Zod schema and controller mapping;
changing a database query affects the PostgreSQL adapter; and changing attendance
event alternation affects the domain function. These concerns are not combined in
one large controller or service.

\subsubsection{Open/Closed Principle}

The design supports several extensions without changing the high-level scan flow:

\begin{itemize}
  \item \texttt{AttendanceService} uses the \texttt{AttendanceRepository}
        abstraction. A different persistence adapter can be introduced while
        keeping the service's orchestration unchanged.
  \item QR validation is expressed by the one-method \texttt{QrCodeValidator}
        contract. The attendance service does not depend on QR token storage or
        hashing details.
  \item The in-memory and PostgreSQL adapters implement the same repository
        interfaces, allowing the implementation to vary independently of the
        service.
  \item \texttt{AttendanceServiceConfig} and an injected clock provide
        configuration seams for cooldown behavior and time-dependent tests.
  \item The \texttt{HRPayrollPort} can be implemented by an HTTP gateway or a
        logging gateway without changing the port's declared contract.
\end{itemize}

The extension points are bounded: QR lifetime and location tolerance are
currently constants in the QR-code domain module, so changing those policies
requires editing that module rather than supplying new configuration.

\subsubsection{Liskov Substitution Principle}

The repository interfaces describe the operations expected by the services:

\begin{verbatim}
export interface AttendanceRepository {
  findEmployeeById(id: string): Promise<AttendanceEmployee | null>
  findLatestRecord(employeeId: string): Promise<LatestAttendanceRecord | null>
  createRecord(record: NewAttendanceRecord): Promise<AttendanceRecord>
}

export interface QrCodeRepository {
  createQrCode(qrCode: NewQrCode): Promise<QrCodeRecord>
  findQrCodeByTokenHash(tokenHash: string): Promise<QrCodeRecord | null>
}
\end{verbatim}

\begin{itemize}
  \item \texttt{PostgresAttendanceRepository} and
        \texttt{InMemoryAttendanceRepository} both implement the attendance and
        QR-code repository contracts. The services can therefore use either
        implementation through the interface types.
  \item Both implementations return \texttt{null} when a lookup has no matching
        employee, attendance record, or QR code, and return domain-shaped
        records when a lookup succeeds.
  \item Both adapters reject a QR code that has already been consumed. The
        PostgreSQL implementation additionally protects consumption and record
        insertion with a database transaction.
  \item \texttt{QrCodeService} implements \texttt{QrCodeValidator}; it can be
        supplied to \texttt{AttendanceService} wherever that validation contract
        is required.
\end{itemize}

The in-memory adapter supports deterministic unit tests, but it does not
reproduce PostgreSQL transaction isolation or concurrent request behavior.
Substitution tests therefore validate ordinary service behavior, not all
production persistence guarantees.

\subsubsection{Interface Segregation Principle}

The module uses small, role-specific contracts instead of making every client
depend on one broad persistence or integration interface:

\begin{itemize}
  \item \texttt{AttendanceRepository} contains only employee lookup, latest-record
        lookup, and attendance creation.
  \item \texttt{QrCodeRepository} contains only QR-code creation and lookup by
        token hash.
  \item \texttt{QrCodeValidator} exposes only the validation operation needed by
        \texttt{AttendanceService}; the service does not depend on QR-code
        creation methods.
  \item \texttt{HRPayrollPort} has only \texttt{sendAttendance}, the operation
        needed by an HR/payroll integration client.
\end{itemize}

\texttt{PostgresAttendanceRepository} and
\texttt{InMemoryAttendanceRepository} implement both repository interfaces
because the same storage adapters serve both attendance and QR-code use cases.
Clients still depend on the narrower interface corresponding to their needs.

\subsubsection{Dependency Inversion Principle}

The high-level attendance workflow depends on abstractions at its persistence
and validation boundaries:

\begin{itemize}
  \item \texttt{AttendanceService} receives an \texttt{AttendanceRepository} and a
        \texttt{QrCodeValidator}; it does not import PostgreSQL or query the
        database directly.
  \item \texttt{QrCodeService} receives a \texttt{QrCodeRepository} instead of
        creating a database connection itself.
  \item The current clock is supplied as a \texttt{() => Date} function to both
        services, making expiration and cooldown behavior testable without
        relying on wall-clock timing.
  \item \texttt{app.ts} supplies the production implementations at startup:
\end{itemize}

\begin{verbatim}
const attendanceRepository = new PostgresAttendanceRepository(pool)
const qrCodeService = new QrCodeService(attendanceRepository)
const attendanceService = new AttendanceService(
  attendanceRepository,
  qrCodeService,
  { cooldownSeconds: 30 },
)
const attendanceController = new AttendanceController(
  qrCodeService,
  attendanceService,
)
\end{verbatim}

This composition root also allows tests to construct the services with
\texttt{InMemoryAttendanceRepository} and a fixed clock. Dependency inversion is
not complete at every layer: the controller is typed against the concrete
\texttt{AttendanceService} and \texttt{QrCodeService}, and the router is typed
against the concrete \texttt{AuthService}. Those dependencies are constructor or
factory-injected, but their public contracts are not separately expressed as
interfaces.

\subsubsection{Limitations}

\begin{itemize}
  \item The HR/payroll port and its HTTP and logging adapters exist, but the
        application composition root does not instantiate them and the
        attendance workflow does not call \texttt{sendAttendance}. A successful
        attendance write adds an outbox row, but no outbox publisher or consumer
        was found in the current backend source. Consequently, delivery to an
        external HR/payroll service is not demonstrated by the current request
        flow.
  \item The in-memory repository does not model PostgreSQL transaction and
        concurrency guarantees. In particular, its tests cannot establish the
        database adapter's behavior under simultaneous scans or database
        failures.
  \item The controller and router use concrete service/authentication class
        types instead of narrower service interfaces. This keeps the current
        implementation straightforward, but makes those boundaries less
        flexible than the repository and QR-validator boundaries.
  \item QR-code lifetime, location tolerance, and the cooldown are not all
        configurable through the application environment: the lifetime and
        location tolerance are domain constants, while the cooldown is supplied
        directly as a value in \texttt{app.ts}.
\end{itemize}
